# Stage D.2 methodology and assignment-evidence audit

The saved Stage D.2 work includes an executed direct-ODE parameter Monte Carlo study, official sampling and plotting utilities, historical-event comparisons, and bounded robustness/antecedent checks. It does **not** include a D.2 Monte Carlo response-surface fit or random-design-variable Monte Carlo arms. Those omissions must remain visible when discussing the broader final-project assignment. This audit reads source code and saved results only; it performs no simulation, sampling, fitting or rewriting of previous outputs.

Machine-readable checks, source hashes and actual API signatures are in [methodology_evidence.json](methodology_evidence.json).

## Actual official implementation

The local official checkout is pinned to revision **`06d7aed5b541ec7fe26a6dc69be6aa7fb610aa02`**, package metadata version **1.2.1**, from [hpgavin/multivarious](https://github.com/hpgavin/multivarious/tree/06d7aed5b541ec7fe26a6dc69be6aa7fb610aa02). Its tracked files are unchanged; the inspection found one untracked `.DS_Store`. The project imports this external checkout explicitly rather than substituting an unrelated package.

The example-local functions are `analysis(v, c)` and `mcs(v_medn, v_covn, N_mcs)`. They are not package algorithms that must be imported under those names. The example's analysis randomizes climate constants, runs its complete official `ode4u` trajectory, and records objective/constraint outcomes. Its Monte Carlo loop samples design vectors and invokes that analysis. The wetland adaptation instead samples and saves each approved parameter vector once, supplies exactly that vector to both physical cases, then records both trajectories' physical outputs, hydraulic validity and safety. It never redraws parameters inside an ODE derivative or separately for paired models.

The professor example and pinned package have API differences: the example expects an unavailable `load_model_npz` export; `compute_model` is module-internal rather than exported from `multivarious.fit`; and its final three `mimo_srs` return variables are unpacked in a different order from the implementation. The earlier [detailed API review](../parameter_uncertainty/professor_method_review.md) records these differences. They were documented rather than repaired by changing official source.

The parameter categories are `K_u`, one common multiplier for `k_ud[0]`, `k_ud[1]` and `k_ur`, and `R_r`. Routing ratios and flow caps remain unchanged. The group factor couples three physical rates; it does not create three independent routing draws. Supports, distributions and cross-group independence are approved exploration assumptions, not locally calibrated uncertainty. The [mapping](../parameter_uncertainty/parameter_mapping.md) and [assumption justification](../parameter_uncertainty/uncertainty_basis.md) preserve that distinction.

The earlier weather pilot is a separate study: 20 saved weather IDs, 16 valid nonfreezing paired trajectories and four explicitly retained cold-domain exclusions. It is not a substitute for the 64-vector parameter experiment, nor evidence for a calibrated heavy-storm or annual flood distribution. Neither current study defines a downstream flood threshold. Initial-reference exceedance metrics are not flood occurrence metrics.

The [Stage C official FIT report](../../../C/docs/c2_fit_summary.md) uses `mimo_srs` to predict **P, T, Rs and W** from weather/history/calendar features. Its saved [specification](../../../C/tables/mimo_srs/model_specification.json) confirms those targets. It is a different dataset and scientific question from fitting uncertain physical parameters to Monte Carlo river peaks or constraint responses. Stage C cannot be counted as the missing D.2/final-project MCS polynomial sensitivity fit, and it was not rerun here.

The pinned top-level `mimo_srs` scales supplied data before its random split and applies a joint input/output outlier rule. A later authorized response-surface task would have to address preprocessing leakage and preserve genuine extreme/unsafe physical outcomes explicitly. Its actual return order ends `testX, testY, testModelY`, and its scalar default scaling argument is inconsistent with the indexed implementation. These are documented implementation issues, not a reason to fit a substitute model during this audit.

## Reading historical status statements correctly

Earlier files retain the scope in force when written. In particular:

- `D/d2_analysis/README.md` describes the **earlier weather pilot** and says no full Monte Carlo or hydrologic spin-up was performed in that task. It does not negate later parameter MCS or the separate antecedent experiment.
- Parameter-study planning text and instructions such as “no commit or push is part of this work” describe their original task, not a permanent prohibition against a later explicitly authorized publication.
- The detailed professor-method review's statement that a surrogate is unnecessary for computing the direct-ODE MCS results is technically narrow. It must not be extended into a claim that final-project item 12 is already satisfied or optional.
- Antecedent documents call their work a bounded interpretation check rather than a final submission report. Consolidation changes navigation and documentation; it does not retroactively expand that experiment or erase its limitations.

This audit leaves all those historical records unchanged. The current consolidated entry point should identify the distinct completed studies and the verified outstanding final-project methods, rather than reinterpret old scopes as new results.
